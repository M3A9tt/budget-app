# UI Designer — Бюрджет

**Задача:** развивать узнаваемый, выразительный и аккуратный интерфейс Бюрджета **на базе уже выбранных решений**, не превращая его ни в шаблонный AI-dashboard, ни в плоскую безликую утилиту. Внешний вид должен усиливать понимание денег и действий.

## 1. Контекст до проектирования

1. Изучи текущие `AGENTS.md` (приоритеты P0–P3, если уже принята их структура), связанные профильные правила и живой код. При расхождении документа и кода выясни, является ли документ **утверждённой целью, действующей реализацией или историческим экспериментом**. Не подменяй утверждённую цель устаревшей реализацией.
2. Для визуального контекста используй точечные источники:
   - **Главная:** `src/home-v5.css`, `src/PersonalNext.jsx`, `docs/glass-home.md`. Пользователь **выбрал стеклянный вариант 1** с мягким шалфейно-лавандовым светом и однострочной датой DD.MM с тонким разделителем; яркий вариант 2 — отвергнутая альтернатива.
   - **Формы:** `src/EntryComposer.jsx`, `src/EntryMoney.jsx`, `src/EntryPicker.jsx`, `src/TransferForm.jsx`, `src/entry-v5.css`, `docs/ENTRY-LAYOUT-2026-11-04.md`. Перевод — эталон иерархии формы; сумма первая, контекст и дополнительные поля не соперничают с ней. Сохраняй утверждённую компактную одноэкранную запись.
   - **Календарь, операции, навигация:** `src/calendar-v5.css`, `src/mini.css`, `src/personal-ui.css`, `src/MiniApp.jsx`, `docs/5.0-visual-review.md`, `docs/personal-interface.md`. Не считай экспериментальные варианты календаря одобренными. Актуальную целевую навигацию бери из принятого ЗАВЕТА, не из скриншота предыдущей версии.
   - **Бренд и текст:** `src/Brand.jsx`, `public/brand/lockup-refined-b.webp`, `src/typography.css`, `docs/brand.md`. Выбранное слитное начертание: символ «Б» уже служит первой буквой, отдельную «Б» не добавлять.
3. Найди готовые визуальные компоненты и аналоги **в той же оболочке**. Не создавай новый набор полей, селекторов, денег, иконок и CSS-токенов, если подходящий уже существует. Не наращивай цепочку поздних CSS-переопределений ради локального эффекта: правь ответственный слой.

## 2. Визуальная грамматика (следует из выбранных экранов)

- **Графитовая основа и мягкое стекло:** тёмный сине-графитовый фон, деликатный зелёно-шалфейный и лавандовый свет, полупрозрачные поверхности, тонкая подсвеченная кромка и сдержанные внутренние блики. Опирайся на действующие токены `personal-ui.css` и выбранные значения `home-v5.css`, а не изобретай новую кислотную палитру. Глубина читается как иерархия, не как фон каждого элемента.
- **Один главный акцент:** на первом экране — денежный результат или основное действие. Крупная светлая сумма, вторичные подписи спокойнее; валюта и комиссия не должны перетягивать внимание. При нехватке денег опасное состояние заметно без опоры только на цвет.
- **Типографика:** локальный `Commissioner`; обычный текст/поля ≈16 px, подписи 14–15 px, узкие подписи навигации 13 px (каталог символов — 12 px); крупная денежная типографика определяется контекстом существующих экранов. Денежные колонки с tabular numerals и выравниванием по правому краю; названия — по началу строки. Не лечи переполнение уменьшением шрифта.
- **Контуры и структура:** один главный заголовок на экран, точные отступы, тонкие разделители для логически связанных строк, достаточно места для нажатия. Не складывай карточку в карточку и рамку в рамку. Последние операции — читаемые строки, **не** отдельный стеклянный контейнер на каждую покупку.
- **Цвет по смыслу:** сохраняй цветовую семантику текущей системы (доход, расход, перевод, корпоративный обед) и собственный акцент выбранного действия; вторичный текст и доступность не зависят только от цвета. Иконка нужна для распознавания, а не украшения.
- **Движение:** плавный вход/выход, раскрытие, переключение и возврат показывают направление и состояние; не задерживают запись денег, не меняют суммы анимацией и не дают швов/вспышек. Обязательно `prefers-reduced-motion`, обычное/hover/active/focus/disabled/loading/error состояния. Для стекла нужен читаемый непрозрачный fallback без `backdrop-filter`.

## 3. Рабочий процесс

1. **Сценарий:** назови задачу экрана и что человек должен увидеть, понять и нажать. Сверь доступность соседних действий, возврат и состояние черновика; если главная проблема в удобстве, подключи `ux-audit`.
2. **Референс в коде:** назови 1–3 существующих компонента/экрана, которые берёшь за образец, и что именно из них переносишь. Укажи, что сохраняешь без изменений (бренд, согласованные решения, финансы).
3. **Варианты по делу:** когда есть реальная визуальная развилка — подготовь 2–3 **различающиеся композицией**, а не только оттенком, альтернативы на одинаковых вымышленных данных и размерах. Объясни различия; для незначительной правки лишние варианты не нужны. Не протаскивай отвергнутые варианты в сборку; зафиксированный выбор — исходная точка.
4. **Реализация:** изменяй минимально необходимый общий компонент и его стили. Сохраняй прежние финансовые команды, маршруты, доступность, пользовательские настройки и режимы. Не переписывай работающую форму ради нового внешнего вида.
5. **Проверка по настоящему экрану:** мобильные 320/390/768 px и широкий 1280 px, а для форм также переломные ширины 421–767 px и низкий viewport. Проверяй горизонтальный скролл, переносы, пересечения, видимость кнопок и сумм, экранную клавиатуру там, где доступна, фокус и возврат, состояния ошибки/загрузки, анимацию во время движения, reduced motion и fallback стекла.
6. **Доказательства:** переиспользуй `npm run test:layout`, `npm run test:personal`, `npm run test:browser`, `npm run build` и относящиеся к экрану `scripts/check-glass-home.mjs`, `scripts/check-brand-integration.mjs`, `scripts/check-entry-layout.mjs`; выбирай применимые, не запускай всё без причины. Для существенной визуальной правки сравни реальные Chromium-снимки двух ревизий на одной фикстуре, дате, DPR и viewport; при возможности используй `scripts/capture-audit-comparison.mjs`. Никаких личных финансовых данных в примерах.

## 4. Оценка результата и границы

В отчёте покажи **до → после** с конкретными отличиями: иерархия, плотность, читаемость, достижимость, состояние взаимодействия. Сошлись на путях файлов, фактически выполненных командах, снимках и ревизиях. **Нарисованный концепт ≠ проверенный интерфейс; Chromium ≠ реальный новичок или физический Telegram WebView.** Если визуальный доступ или среда отсутствуют, честно укажи ограничение.

**Разделение ответственности:** `ui-designer` создаёт и уточняет визуальное решение; `ux-audit` независимо проверяет освоение и сценарии; `finance-qa` подтверждает денежные инварианты; `grill-me` помогает при спорном выборе. ЗАВЕТ всегда важнее локальных инструкций скилла. Не плодить лишние дизайн-документы, стили и новые подсистемы.
