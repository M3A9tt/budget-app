# UX-аудит Бюрджета

**Цель:** интерфейс, который понятен новому пользователю и остаётся визуально выразительным. Это проверка сценариев, а не конкурс макетов.

## Перед аудитом

1. Прочитай `AGENTS.md`, затем относящиеся к задаче `docs/UX-RESEARCH-2026-11-01.md`, `docs/TASK-FIRST-UX-2026-11-01.md`, `docs/ENTRY-LAYOUT-2026-11-04.md`, `docs/brand.md`. Старые отчёты — исторические свидетельства; действующее поведение устанавливай по текущему коду.
2. Изучи затронутые разделы и общие компоненты, особенно `src/MiniApp.jsx`, `src/EntryComposer.jsx`, `src/EntryMoney.jsx`, `src/EntryPicker.jsx`, `src/TransferForm.jsx`, `src/MoreMenu.jsx`, `src/PaymentsPage.jsx` — только если они действительно участвуют в сценарии.
3. Выбери 2–5 задач пользователя (первый запуск, запись расхода/дохода, поиск операции, платёж/перевод, возврат и исправление ошибки). Не ориентируйся исключительно на привычки разработчика.

## Как проверять

- Пройди путь от точки входа до подтверждённого результата: видимость действия, число и смысл переходов, возврат, сохранение черновика, обратная связь об ошибке, обновление зависимых данных.
- Проверь и обычные, и крайние состояния: пусто, длинные названия, большие суммы, длинная история, просрочка, частичная оплата, загрузка, ошибка сети, отключённый модуль.
- Проверь мобильный и широкий экран, минимум 320/390/768/1280 px там, где меняется компоновка. Оцени реальный размер текста и области нажатия, переполнение, фокус, клавиатуру, системное уменьшение анимации и читаемость без цветовой подсказки.
- Ищи признаки шаблонного «нейрослопа»: одинаковые бесцельные карточки, вложенные рамки, декоративные градиенты без иерархии, избыточные инструкции, дубли действий, неочевидные иконки, функции в глубоком меню. **Не удаляй** фирменную глубину, фирменные цвета, хорошую типографику и нужные предупреждения ради минимализма.
- Сопоставляй видимый экран с денежным результатом. «Удобнее» не означает «можно скрыть финансовый смысл или подтверждение».

## Доказательства и инструменты

- Переиспользуй имеющиеся проверки: `npm run test:usability`, `npm run test:layout`, `npm run test:browser`, при необходимости `npm run test:entry` и `npm run test:personal`; исходники — `scripts/check-intuitive-browser.mjs`, `scripts/check-entry-layout.mjs` и соседние скрипты.
- При изменениях сравни **реальные снимки** исходной и новой ревизии на одинаковых вымышленных данных, дате и размерах; по возможности используй `scripts/capture-audit-comparison.mjs`. Отделяй технический браузерный прогон от реального теста новичком и физического Telegram WebView.
- Не придумывай измеренные метрики, скриншоты и факты проверки. Если инструменты недоступны, явно назови границу: анализ кода/эвристика, не пользовательское подтверждение.

**Результат:** 3–7 приоритетных наблюдений с местом, воспроизводимым сценарием, доказательством, предлагаемым исправлением и регрессионным риском. По запросу на реализацию переиспользуй существующие компоненты и проверь затронутую цепочку. Не создавай отдельный UX-фреймворк и новые отчёты без необходимости.
