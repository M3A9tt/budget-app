# «Финансы» 2.0 — первая тестовая версия

Это отдельная переработка. Опубликованный `budget.apersunov5.workers.dev` не изменён. Не загружайте новую сборку поверх старой до экспорта данных и проверки переноса.

## Что работает в новой сборке

- Единая финансовая логика добавления, изменения, удаления и отката операции. Фактическое списание в валюте счёта записывается в операцию; смена курса не меняет возврат денег.
- Комиссия перевода списывается один раз. Переводы между разными валютами временно запрещены до формы фактического обменного курса.
- Ввод одной строкой на главной: `кофе 180 Сбер`, `обед 379,50`, `зарплата 33000 Т-Банк`. Перед записью — проверка карточки, для расхода можно поправить категорию. При нескольких счетах без названия — уточнение.
- Описание в обычном и быстром вводе необязательно. Подсказки берут новые описания. Обычный ввод открывается с сегодняшней датой.
- Русская десятичная запятая, проверка суммы, защита от устаревшего редактирования/отката.
- JSON-импорт проверяет структуру и дубликаты; остатки переносит без пересчёта. Старые валютные операции с неизвестным списанием помечает для сверки и блокирует их денежное редактирование/удаление.
- Локальная копия шифруется AES-GCM после ввода PIN; сохранения выполняются последовательно. Есть предыдущая зашифрованная копия. Ошибка сохранения показывается в интерфейсе. PIN больше не кешируется открытым текстом в sessionStorage.
- Будущие месяцы не начисляют экономию обедов.
- Постоянные расходы — план платежей с ручным подтверждением фактической оплаты, а не автоматическое списание.
- Удаление счёта/категории, используемых в истории, запрещено.
- «Баланс» главной переименован в «Результат месяца»: это не реальный остаток банка.

## Ограничения этой итерации

Новая веб-сборка сохраняет изменения только на устройстве. Запись в общую старую строку Supabase отключена намеренно. Старое облако может использоваться только как источник первоначального переноса, если локальные данные пусты и PIN подходит. Между устройствами новая версия пока не синхронизируется.

Вход требует PIN при открытии; биометрия сама по себе не может расшифровать данные. Смена PIN отключена до безопасной миграции ключа. PBKDF2/соль и проверка старого PIN сохраняют совместимость с прежним облаком; это не окончательная переделка авторизации. Короткий прежний PIN остаётся слабым секретом.

Обеды по-прежнему предполагают оплату компанией; личная доплата, производственный календарь и незаполненные дни ещё требуют отдельного этапа. Долги и цели ещё не связаны с реальным движением денег по счетам. Полной новой модели свободного остатка до зарплаты пока нет.

Напоминание браузера работает только пока приложение открыто; гарантированное фоновое расписание реализуется сервером бота. Масштабирование страницы разрешено, но полное визуальное и мобильное тестирование ещё не проведено.

## Как проверить локально

Нужны Node.js 24+ и npm (тесты SQL используют встроенный node:sqlite).

```sh
npm ci
npm test
npm run dev
```

Используйте localhost или HTTPS: Web Crypto требует безопасного контекста. Не запускайте `dist/index.html` двойным кликом. Сборка: `npm run build`; просмотр сборки: `npm run preview`.

## Перенос данных

1. В старом приложении выгрузить JSON и сохранить его независимо от браузера.
2. Открыть новую версию на отдельном адресе/локально. Создать PIN для новой локальной копии. При ошибке чтения старого облака выбрать «Открыть пустую новую версию для импорта JSON».
3. Настройки → Импорт → выбрать старый JSON → проверить количество операций и счетов в подтверждении.
4. Сверить остатки каждого счёта, обеды, долги, цели, постоянные платежи и количество операций. Новая версия не чинит сомнительные старые остатки автоматически.
5. Выполнить экспорт из новой версии; проверить повторный импорт в другом тестовом браузере.
6. После сверки подключать новый сервер. До этого старое приложение остаётся рабочим.

При импорте старые данные доступны через открытый JSON-файл; храните его как личный финансовый бэкап. Встроенная локальная зашифрованная резервная копия лежит в `finance-app-encrypted-v2-previous`; автоматического интерфейса её восстановления пока нет.

## Telegram и серверный API

В `server/worker.js` — отдельный сервер Cloudflare Workers с D1, использующий то же финансовое ядро.

Реализованы:

- только один разрешённый Telegram ID и только личный чат;
- секрет webhook, отдельный секрет API, проверка доступа до обращения к базе;
- разбор сообщения → карточка → кнопка «Записать»;
- идемпотентность записи: повтор кнопки не создаёт вторую покупку;
- `/today`, `/week`, `/month`;
- серверные ежедневные, недельные и месячные отчёты;
- импорт снимка базы с проверкой ревизии и атомарные изменения счёта/операции;
- API: `GET/PUT /api/v1/state`, `POST /api/v1/transactions`, `GET /api/v1/summary`.

Это подготовленный код, а не подключённый бот. Сервер не развёрнут, SQL-транзакции проверены локально на SQLite; Cloudflare D1 и Telegram в реальной среде не проверены. Веб-интерфейс этой итерации ещё не читает этот API — после развёртывания потребуется подключить его и завершить конфликтную синхронизацию. До этого нельзя одновременно вести независимый учёт в новой локальной версии и серверной базе как будто они едины.

### Настройка сервера следующим этапом

Создать отдельную D1-базу, применить `server/schema.sql`, скопировать `wrangler.example.jsonc` в `wrangler.jsonc`, вписать ID новой базы и свой Telegram ID. Секреты установить через Cloudflare, не в исходниках:

- `API_TOKEN`: длинный случайный токен владельца;
- `TELEGRAM_BOT_TOKEN`: токен от BotFather;
- `TELEGRAM_WEBHOOK_SECRET`: отдельный длинный случайный секрет.

После развёртывания задать Telegram webhook на `/telegram/webhook` с `secret_token`. Импортировать JSON в новую D1 через авторизованный `PUT /api/v1/state`: тело `{ "expectedRevision": 0, "data": <JSON-бэкап> }`. API-токен передаётся только в заголовке `Authorization: Bearer ...`. Не передавайте токен или PIN в сообщения боту.

В новой серверной модели Worker читает финансовые данные в базе и может строить сводки. Это не сквозное шифрование PIN из браузера; база защищается серверной авторизацией и средствами Cloudflare. Перед реальным переносом эту модель нужно принять явно.

Тестовое расписание кода: каждый день в 21:00 Москвы, воскресенье — дополнительно неделя, первое число — предыдущий месяц. Это предложенные значения, пользователь время ещё не выбирал; их следует настроить перед запуском. Cron будит сервер каждый час. Сводки сейчас вычисляются программой, а не моделью ChatGPT. Автоматизации ChatGPT не созданы: авторизованный инструмент к новой базе ещё не подключён.

API пока не поддерживает удаление/редактирование через внешнего помощника, отзыв/ротацию отдельных токенов и банковскую интеграцию. Полный backend нужно проверить на D1/Telegram, добавить восстановление после сетевых ошибок. Окно сбоя между отправкой отчёта и фиксацией доставки требует более надёжного outbox; текущая таблица предотвращает обычные повторные запуски, но не обеспечивает абсолютную гарантию доставки.

## Проверка выполненной работы

32 автоматических теста прошли; production-сборка Vite выполнена. Проверены финансовые инварианты, миграция без изменения остатков, ошибочный импорт, защита устаревших изменений, encrypted storage, большой payload, неверный PIN, запрет открытого fallback, московские даты, закрытый API без секретов и разделение обедов в сводке.

Проверки не заменяют запуск на вашем телефоне, сверку настоящего JSON-бэкапа и интеграционные тесты облака. Архив не содержит настоящих финансовых данных, токена Telegram или сервисного ключа.
