# 4.1.0 — проверка интерфейса и связанных действий

База: 4.0.2, commit e32030ebeb7a589611eec14c8abb63f60e3e80bc.

## Воспроизведённые проблемы

1. После открытия сверки «Альфа» и нажатия карточки «Яндекс» select продолжал содержать alpha. Браузерный тест до исправления завершался `alpha !== yandex`. Форма пересоздаётся при смене выбранного счёта, чтобы defaultValue не удерживал прежнюю цель.
2. После открытия платежа из месячного календаря сбрасывались горизонт и переключатель будущих доходов; выбранный день мог оказаться за пределами окна и заменялся сегодняшним. Состояние календаря теперь живёт на уровне приложения и передаётся обеим оболочкам календаря.
3. «Оплатил» в графике рассрочки сразу списывало остаток платежа. Кнопка открывает общую форму через prepareEvent. Частичную оплату и её изменение ведёт существующий ledger; строки оплат открывают исходные операции. Выбранный раздел платежей сохраняется после возврата.
4. Сумма разовых обязательств считалась только до следующего дохода, хотя соседние суммы кредитов и долгов означали полный остаток до погашения. Полный остаток разовых расходов теперь использует все неоплаченные разовые планы. Ближайший бюджет по-прежнему использует прежнее ограниченное окно и не вычитает дальние платежи.
5. «Все» последние операции на главной переносило старый поиск и фильтр доходов. Этот переход очищает фильтры; обычный возврат после редактирования их сохраняет.

## Завершённый сценарий перевода

Одна TransferForm используется из счетов, вкладки записи и ввода одной строкой. Быстрый ввод использует существующий parseOwnTransfer. Видны направления, доступные счета, комиссия и будущие остатки; нулевой счёт можно выбрать получателем. Сумма перевода не становится расходом: только комиссия проходит через putTransaction.

Перед подтверждением у черновика есть стабильный transferId. transferMoney принимает его как существующий ID перевода: точный повтор возвращает прежнее состояние, а тот же ID с другими полями отклоняется. Это защищает повторную попытку после неопределённого результата сети. Старые вызовы без ID продолжают создавать ID внутри модели. Ни схема, ни формат уже сохранённых переводов не меняются.

## Интерфейс

В шапке оставлены обновление и настройки; второстепенные действия раскрываются меню с текстовыми названиями. Сообщение об ошибке прокручивается в поле зрения. Длинные подписи и поля перевода проверяются в узкой вёрстке. Календарь, платежи, форма операции и история продолжают ссылаться на одни сущности.

## Проверки и пределы

- Чистые модели: перевод с комиссией, точный повтор и конфликт ID; дальние обязательства и ближайший бюджет.
- React и реальные обработчики приложения: восстановление календаря, исходная операция оплаты, сохранение черновика перевода, очистка фильтров.
- Chromium: переключение счёта сверки, платёж вне исходного горизонта, перевод одной строкой с комиссией, частичная рассрочка и изменение той же оплаты, ширины 320/360/390/430/768/1280.
- Полный набор тестов, production build, Worker bundle, CI и release guard.

Финансовая схема не меняется, старые остатки и история автоматически не пересчитываются. Проверки идут на вымышленных профилях; физические телефоны и реальный Telegram-клиент автоматически не тестируются. Независимый бэкап и миграция по-прежнему обязательны перед будущим изменением финансового хранилища.
