# 4.8.0 — независимые копии, очередность картинок и контроль доставки

Следующий этап ТЗ от 29 октября 2026 года. Основа сравнения — `7e2905ddd5458fb5dbac1b117b1f0700f4daa35e` (4.7.1). Основной финансовый JSON, остатки, история и команды не мигрируют в этом выпуске.

## Что реализовано

### Независимая резервная копия — F18

Workflow `Independent database backup` экспортирует **существующую budget-staging D1**, восстанавливает SQL в изолированную SQLite, проверяет целостность, наличие финансовых таблиц, точные JSON профилей, ревизии и квитанции. Затем сжимает SQL и шифрует новым случайным AES-256-GCM ключом; ключ оборачивается RSA-OAEP-SHA256 (RSA 3072). Метаданные защищены AES-GCM, SQL и зашифрованный файл имеют SHA-256. Версия формата и исходный commit сохраняются.

Зашифрованный файл и безопасный manifest сохраняются в GitHub Actions, вне Cloudflare D1. Запрошенный срок — 90 дней, фактическое `expires_at` определяется политикой репозитория. Удаление workflow run удаляет его артефакты. Это независимость от потери рабочей базы, а не отдельная система от GitHub или бессрочный архив.

Расписание: ежедневно в 03:17 по Москве; GitHub может задерживать запуск. Та же проверенная копия обязательна перед выкладкой: `deploy` зависит от `verify` и `safety_backup`. При неуспехе экспорта, проверки, шифрования или сохранения артефакта публикация не начинается. Экспорт D1 кратковременно блокирует запросы к базе; ночное расписание снижает влияние. Имена секретов и существующие полномочия не менялись.

Закрытого ключа нет в репозитории, Worker, Actions secrets и артефакте базы. Отдельный комплект восстановления передан владельцу. В репозитории есть только `config/backup-public-key.pem`. Отпечаток: `f7acfd4a7e12f3bb43e63a44dbcc6c63531ad259c30256f15eabc92189ed6c9f`.

Wrangler печатает временную ссылку на открытый SQL: вывод экспортёра намеренно не попадает в журнал workflow. Временный SQL удаляется в `finally`, в артефакт попадают только `database.burget.enc` и `manifest.json`. Восстановление выполняется локально командой `node scripts/restore-db-backup.mjs ARCHIVE PRIVATE_KEY NEW_SQL_PATH`: новый SQL создаётся только после проверки AES-GCM и точной контрольной суммы; существующий файл не заменяется. Рабочая база автоматически не восстанавливается.

Независимая копия и полный перевод хранилища — разные критерии. F18 остаётся частичным в отношении полного удаления профиля и завершения миграции. Запуск первого реального копирования и проверка сохранённого артефакта проверяются при публикации; одни unit-тесты этого не доказывают.

### Справедливая очередь картинок — F19

Рендеры используют устойчивую общую очередь в D1 и один эксклюзивный lease. Ручные запросы идут перед новыми фоновыми отчётами; после 2 секунд фоновое задание получает ту же приоритетность. Внутри приоритета сначала получает ход пользователь с самой старой предыдущей попыткой, затем его запросы. Предел ожидания — до 8 секунд, по умолчанию 3,5; при истечении остаётся полный текст без дополнительной цепочки сообщений.

Очередь ограничена 4 заявками на пользователя и 64 всего. Один пользователь по-прежнему ограничен 6 новыми картинками в сутки, сервис — 24. Кэш не расходует квоту. Одинаковый снимок объединяется, в том числе между независимыми экземплярами Worker. Умершие ожидающие заявки истекают; lease запущенного рендера — 45 секунд. В очереди нет копии финансового профиля. Это справедливое распределение ограниченного ресурса, не неограниченная производительность.

### Безопасная диагностика и единая политика доставки — F14, F20

В боте: «Ещё → Инструменты → Владелец → Состояние сервиса». Владелец видит успешные сохранения, конфликты, сбои, длительность, картинки/кэш, возраст очередей и состояние фонового обхода. Авторизованный owner API: `GET /api/v1/admin/operations`. Другому пользователю возвращается 403.

Хранятся только часовые агрегаты из фиксированного набора имён и кодов, сумма/максимум длительности. Пользователь, сумма, текст операции, токен и исходное исключение не сохраняются. Окно обзора — последние 24 часа с точностью до часового интервала; срок агрегатов — 30 дней. Ошибка записи метрики не меняет успешный результат финансовой команды.

Общая политика применяется и к напоминаниям, и к анонсам релиза:

| Результат | Действие |
| --- | --- |
| 429 | Очередь до разрешённого повтора |
| 400 / 403 | `blocked`, без ежечасового повтора, даже если известно, что сообщение не принято |
| Сетевой разрыв / неопределённый результат | `uncertain`, без слепой повторной отправки |
| Telegram принял, запись квитанции не удалась | Сначала завершается квитанция, новое сообщение не отправляется |
| Worker умер во время отправки | После lease результат становится `uncertain` |

Ручной режим и одна общая сводка подавляют отдельную рассылку релизов. Полная история обновлений остаётся в «Что нового». Старые неотправленные анонсы заменяются актуальным, а не выгружаются пачкой. Неопределённые/заблокированные результаты остаются для разбора; гарантия exactly-once для внешнего Telegram не заявляется.

Сценарии выполнены над исходными модулями двух ревизий в отдельных SQLite. Во всех случаях профиль содержит 1000 ₽, операций нет, исходный JSON финансового профиля остаётся побайтно неизменным. Для логических исправлений приведены точные числа вместо выдуманных изображений интерфейса. Повторяемый запуск: `node scripts/capture-operations-comparison.mjs PATH_TO_BASELINE_CHECKOUT`.

## Проверки и границы результата

- Локально: 495 тестов, production build, сборка Worker, production dependency audit — 0 находок.
- Расшифровка проверена с **реальным отдельным ключом**, точные исходные байты совпали. Повреждение, неверный ключ, усечение и существующий выходной файл отвергаются. Отдельно проверены деньги, historical amountRub/accountAmount, связи, ревизии и старые квитанции после восстановления.
- Проверены очередность разных пользователей, приоритет/старение фоновых заданий и объединение одинакового рендера между двумя независимыми экземплярами.
- Chromium локально недоступен из-за повреждённой загрузки браузера в среде. Оба Chromium-набора, Linux и Windows обязательны в GitHub CI **финального commit**; публикация зависит от их успеха.
- Личные финансовые данные не читались для аудита или интерфейсных фикстур. Рабочий SQL обрабатывается только автоматическим контуром резервного копирования, без вывода содержимого и без финансовых записей.
