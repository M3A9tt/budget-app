## Воспроизведённые проблемы и изменения

1. **Потеря связи оплаты с планом.** После подтверждения `putTransaction({...tx, recurringId: undefined})` превращал оплату в обычную покупку; период снова становился доступен. Теперь редактирование не удаляет и не заменяет `recurringId`, в том числе после удаления будущего графика. Удаление операции и откат продолжают работать через существующий ledger.
2. **Недостоверные пропуски.** `skipPlanned` принимал невозможную дату, день вне недельного графика и период плана на паузе. Теперь проверяется активность, реальный календарный период, привязка к графику и отсутствие оплаты. Повторный пропуск идемпотентен. При чтении бэкапа также проверяются календарные периоды; прежние пропуски сохраняются после изменения даты будущего графика.
3. **Расхождения валютных итогов.** Три старые операции по 0,05 USD при курсе 201,5 давали 30,225 в промежуточных данных и 30,23 после округления общего итога вместо суммы трёх оценок по 10,08. Теперь валютный fallback округляет каждую операцию, а суммы складываются в копейках. Сохранённый `amountRub` имеет приоритет. Исходные записи и остатки не переписываются.
4. **Повреждённый бэкап принимался до падения экрана.** Объект вместо имени счёта, объекта ID, `null` в истории или вложенных платежах и объекты в тегах проходят проверку до использования. Ошибки объясняются; записи не отбрасываются и не заменяются вымышленными значениями.
5. **Зависание запроса и потеря статуса ошибки.** Запрос не имел предельного времени, а HTML вместо JSON терял HTTP status. Теперь таймаут 15 секунд охватывает запрос и чтение тела; таймер всегда очищается. Неясный результат сохранения повторяется один раз с тем же receipt, затем помечается `uncertain` для существующей сверки состояния. Нечитаемый 200 также считается неясным результатом; 4xx не повторяется. Офлайн получает понятное сообщение.
6. **Лишняя вычислительная работа.** Для каждого периода выполнялся проход по всем операциям. Индекс оплаченных периодов и Set пропусков строятся один раз на расчёт, без долгоживущего кэша и риска устаревания.

## Полезные новые возможности и UX

- В существующей карточке плана появилось раскрытие «Пропущенные периоды». Оно показывает сначала пять последних периодов, остальные доступны через «Ещё периоды».
- «Вернуть в план» снимает только пропуск. Счета, расходы и доходы остаются прежними; фактическая операция требует обычного подтверждения. Пауза и изменённая дата начала графика сохраняются. Старые периоды до нового начала не появляются автоматически.
- Сбой React или загрузки ленивого модуля открывает понятный экран с кнопкой обновления. Исключение не показывается пользователю; код не очищает ни серверный бюджет, ни локальные копии.
- Из подготовленной ветки включена навигация бота с редактированием карточек, где это разрешает Telegram, и без постоянно повторяющейся ссылки на миниаппу. Отдельные чеки и уведомления сохраняются.

## Совместимость, данные и выпуск

- Версии схемы D1, полного бэкапа и `burget-operations` v1 не меняются; SQL-миграций нет.
- Реальная база, пользовательские данные и секреты при локальных проверках не менялись. Использовались фиктивные данные и локальные SQLite/D1-имитации.
- Повреждённый файл отвергается с ошибкой; оригинал остаётся у пользователя. Автоматическая «починка» финансовых сумм и молчаливое удаление записей не выполняются.
- Для выпуска используется существующая ветка `codex/multiuser-staging-20261013` и её CI. Развёртывание подтверждается отдельно по завершившемуся deploy job. Существующая инфраструктура объявляет опубликованный патчноут пользователям.
- Для отката кода сохраняется предыдущий SHA. База не заменяется старым снимком: перед любым восстановлением данных нужен независимый актуальный экспорт и сверка появившихся после выпуска операций.

## Оставшиеся ограничения

- Старый `main` и открытый PR #1 остаются отдельным вопросом управления релизами. Перенос ветки по умолчанию может затронуть внешние Pages/Vercel; их текущие настройки не подтверждены. Этот выпуск не переключает неизвестные внешние deployment targets.
- Локальная проверка D1-совместимости через SQLite не заменяет реальные bindings Workers; штатный deployment smoke check проверяет отдельную метатаблицу и рендер фиктивной карточки.
- Проверка физических Telegram WebView, реальной доставки и поведения старых сообщений требует настоящего клиента; CI Chromium не заменяет её.
- Офлайн-очередь финансовых изменений не добавлена. Неясное сохранение сверяется с сервером; приложение не обещает отправить изменения автоматически в фоне.
- Полное отделение классического архивного интерфейса остаётся техническим долгом: он загружается лениво, но его chunk превышает 500 КБ. Объём предупреждения не скрыт изменением порога.
- Восстановление переводов с отсутствующими историческими связями комиссии нельзя надёжно реализовать угадыванием. Будущий общий редактор переводов должен вводить явную связь и проверенную совместимую миграцию, сохраняя исходные записи.

Следующие приоритеты: согласовать основную ветку и подтверждённые окружения, добавить интеграционные проверки в runtime Workers, проверить реальные Telegram-сценарии, затем развивать общий редактор переводов и безопасное восстановление диагностической копии устройства.
