# Доступ для владельца и друга

Новая версия использует общий бот и интерфейс, но отдельные бюджеты по проверенному Telegram ID. Профиль не выбирается параметром запроса, заголовком или импортируемым JSON. Каждому принадлежат операции, счета, цели, долги, настройки, ревизии, резервные копии, idempotency-ключи и отчёты. Веб-код выдаёт сессию тому пользователю, который получил код в своём личном чате бота.

## Настройка

1. До изменения работающего сервера экспортируйте свой свежий JSON и резервную копию D1. Сначала проверить обновление в staging.
2. Проверьте `TELEGRAM_OWNER_ID`: это именно числовой Telegram ID первоначального владельца, не username и не ID друга. Он определяет, кому принадлежит старая общая база.
3. Друг может отправить боту `/id` или `/start`: бот ответит его ID без доступа к финансовым данным. Укажите `TELEGRAM_ALLOWED_IDS` как строку с числовыми ID приглашённых через запятую: `222222222,333333333`. Владелец разрешён автоматически. Пустая строка разрешает только владельца. Публичная регистрация не включена.
4. На той же базе D1 выполните добавочную схему:

```sh
npx wrangler d1 execute ИМЯ_БАЗЫ --remote --file=server/multiuser-migration.sql --config=server/wrangler.jsonc
```

5. Соберите интерфейс и загрузите Worker с обновлёнными vars. Это серверное обновление: статическая загрузка `dist` в Pages не добавляет API или cron. Для существующей версии на Pages потребуется отдельный Worker/API либо переход к Worker, который обслуживает интерфейс и API вместе.
6. Владелец открывает Mini App первым и сверяет остатки. Друг отправляет тому же боту `/start`, открывает Mini App и добавляет свои счета. Чтобы использовать браузер, каждый получает свой код командой `/web`.
7. Проверить двумя аккаунтами: владелец видит свою историю, друг — пустую базу; запись друга не меняет остатки владельца; отчёты приходят каждому в его чат. Проверить веб-вход отдельно для обоих.

## Миграция

Старые таблицы остаются нетронутыми. При первом обращении владельца или cron старое состояние `finance_state.id='owner'` однократно копируется в `user_finance_state` с его Telegram ID, сохраняя JSON, остатки и ревизию. История резервных копий, idempotency-ответы и отметки отправленных отчётов также копируются для владельца. Существующий новый профиль не перезаписывается. Друг никогда не наследует эту базу.

Если старый сайт хранит данные только в браузере или Supabase, автоматический перенос из D1 неприменим: владелец импортирует свой свежий JSON в свой профиль. У каждого импорт заменяет только его бюджет.

Старые одноразовые веб-коды и веб-сессии не действуют — получить новый `/web`. Старые таблицы сохранены для восстановления. Обновлённый сервер пишет только в новые таблицы. Не переключаться между старым и новым сервером после начала учёта без экспорта новых записей: старый сервер не видит многопользовательскую базу.

## Доступ и ограничения

Удаление ID из `TELEGRAM_ALLOWED_IDS` блокирует и Telegram-вход, и ранее выданные веб-сессии. Данные не удаляются. Telegram callback проверяет владельца черновика. Bearer API_TOKEN по умолчанию относится только к `TELEGRAM_OWNER_ID`; опциональный `API_USER_ID` задаёт один профиль на сервере, а клиентские параметры не могут его переключить. Не передавайте административный токен другу.

Сводки и напоминания берут личные настройки и отправляются в личный чат соответствующего ID. Обычные повторы cron отсеиваются отдельно для каждого пользователя. Гарантия exactly-once при сбое Telegram по-прежнему отсутствует.

75 тестов прошли, включая два пользователя с одинаковыми ID счетов/ключами повторов, попытки подмены профиля, миграцию, отзыв доступа, веб-сессии, чужие callback и рассылку. Build успешен. Живой сервер и два реальных Telegram-аккаунта в этой сессии не проверены. Production и GitHub main не изменены.
